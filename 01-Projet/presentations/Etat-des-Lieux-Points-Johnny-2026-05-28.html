1. Point Johnny du 05/05 — où on en était

Au point superviseur du 5 mai (Week 4), trois sujets majeurs étaient sur la table.

Sujet 1 — Échec retentissant de la baseline B2 (embedding JP)

Setup : embedder les 118 112 jurisprudences pénales (CC + CA + TJ) avec multilingual-e5-base (768 dim, contexte 512 tok), embedder les 8 questions CRFPA pénal, retrouver les JP par cosine, puis remonter aux articles via le graphe biparti.

Résultat affiché : Sretrieval = 0,158 (au-dessus du plafond LLM 0,095). En apparence : OK.

Diagnostic profond :

  • Rang médian gold JP : 76 782 / 118 112 — les arrêts gold n'apparaissent jamais dans le top-10 ni même top-1000.
  • S̄jp = 0,000 sur toutes les 160 combinaisons (4 stratégies × 5 K × 8 questions).
  • Le score "positif" venait uniquement du recall articles (0,315), gonflé par over-retrieval (precision = 3,67 %).

Conclusion : le bottleneck n'est pas la stratégie d'agrégation (union/intersection/majority/weighted), c'est l'encodeur lui-même. multilingual-e5-base n'est pas entraîné sur du juridique français ; les JP sont longues (10-50k caractères), narratives, hétérogènes (CC summary 150 tok vs CA/TJ texte brut). Le mean-pooling sur chunks dilue le signal dans le boilerplate procédural.

Sujet 2 — Idée Phase D : embedder les articles, pas les arrêts

Intuition : une question CRFPA cible un point de droit codifié (article LEGI), pas un récit factuel. Les articles sont courts (~500 chars médian), juridiquement structurés, ~87k vs 118k+. On inverse le pipeline :

Question → embed → top-K articles → JP qui citent ces articles (back-edge graphe)

Prérequis : récupérer le texte intégral des articles via Légifrance / dump LEGI DILA. Cela devient la Priorité 2 de la roadmap.

2. Point Johnny du 26/05 — où on est arrivé

Trois semaines plus tard (Week 7), la situation a changé de régime.

Changement qualitatif, pas quantitatif : le 5 mai, aucune information utile ne sortait du top-K. Le 26 mai, 5 à 7 questions sur 38 sont exploitables au critère dur (recall@10 articles ≥ 0,5 ET recall@5 JP via graphe ≥ 0,5).

3. Travail #1 — Pivot JP-first → article-first

3.1 Architecture du pipeline (4 étages)

1. Diagnostic longueurs (token-stats BGE-M3 p99/p100)
2. Ingestion LEGI (dump DILA → SQLite 1,7 M articles)
3. Embedding articles (BGE-M3 1024 dim, L2-normalisé)
4. Évaluation recall@K + back-edge JP via graphe

Invariant central : la clé pair_key (ex. code_penal:222-23) relie nœud du graphe, texte LEGI, et ligne d'embedding. Alignement positionnel lossless, donc l'Étape 2 (laplacien éventuel) récupère les embeddings sans jointure.

5.3 Statut et extensibilité

Pipeline branche-agnostique ✓ : prompt templatable, whitelists dynamiques tirées du PDF, anonymisation pure. Pour étendre à civil / admin / social : (1) fournir les Jurisclasseurs correspondants en PDF, (2) ajuster éventuellement le prompt aux thèmes branche, (3) relancer run_full_pipeline_on_cluster.py.

Infrastructure : vLLM 0.19 + OpenAI API compatible, modèle Gemma 4 26B-A4B AWQ-int4 sur L40S 48 Go (utilisation 34-36 Go), durée GPU ~8h pour pénal complet, cluster mm (QoS dédiée, 8 GPUs).

6.5 Méthode #4 — JP-summary direct (en cours d'éval)

Pipeline :

2. embed BGE-M3 1024d (1h26, 456 MB, batch=32)
3. cosine Q @ emb_jp_synthese.T sur 38 questions
4. comparer aux méthodes via-graph et hybrid

6.6 Le mystère « jp_direct vs jp_via_graph capturent des questions différentes »

Définitions précises :

MéthodeCe qu'elle faitSignal exploité
jp_direct cosine(Q, emb_jp_synthese) → top-K JP directement Sémantique textuelle : la question ressemble-t-elle à la synthèse de la JP ?
jp_via_graph Top-K articles via cosine, puis JP qui citent ces articles via G[:, top_K_cols].sum > 0 Structurel via graphe : la JP cite-t-elle les articles que la question vise ?
jp_hybrid_max Union top-K direct + via-graph, ordre du direct préservé Naïf → sous-performant (cf. plus bas)

6.8 Lecture des résultats

  • Direct catche PENAL-Q3 (fusion-absorption articles 121-1/121-2) : les synthèses de cassation racontent le même scénario que la question → similarité textuelle forte.
  • Via-graph catche PP-Q2 (garde à vue, CPP:63) : la JP gold cite directement l'article, le back-edge l'attrape immédiatement.
  • Union théorique = 3/7 questions distinctes en DUR, 5/7 en FACILE. Mais hybrid_max n'y parvient pas car il écrase les hits via-graph qui arrivent loin dans le ranking direct.
  • → Reciprocal Rank Fusion (RRF) est la solution prochaine.

6.9 Pourquoi seulement 7/38 questions évaluables JP-side

La résolution du gold JP repose sur une regex pourvoi Cour de cassation stricte : \d{2}-\d{2}\.\d{3} (ex. 22-14.567).

Cas non couverts par cette regex (31 questions sur 38) :

  • Arrêts CA/TJ référencés par numéro de rôle (1998-2549, 1362/00)
  • CEDH/CJUE via ECLI (ECLI:CE:ECHR:2023:...)
  • QPC Conseil constitutionnel (n° QPC)
  • jp_attendues = [] sur civil/affaires/admin (gold non défini ou JP non-CC)

Fix planifié : avec la DB OVH (source_id + numero + court), résoudre CA/TJ par numéro de rôle, ce qui étend l'éval à beaucoup plus de questions.
