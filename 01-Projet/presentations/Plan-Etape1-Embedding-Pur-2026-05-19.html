L'ordre n'est pas arbitraire : l'Étape 1 fixe le plancher sans graphe ; chaque étape lève le verrou de la suivante.

1. Approche retenue

Objectif d'Étape 1 = plancher de performance, pas un concours de modèles — le multi-modèles était déjà le cadrage raté de Phase B. Un seul encodeur, baseline propre.

OptionDécisionRaison
A. BGE-M3 seul ✓ Retenu 8 192 tokens, multilingue, self-hosted, sorties dense/sparse/ColBERT utiles plus tard. Satisfait toutes les contraintes, dont « ne jamais tronquer ».
B. BGE-M3 + Jina-v3 Écarté (YAGNI) 2× compute, comparaison ambiguë. Jina-v3 (CC-BY-NC, SOTA long-doc) reste le challenger n°1 si le plancher est insuffisant.
C. voyage-law-2 Hors périmètre Légal-spécialisé, 16k — mais API payante, incompatible avec le choix dump ouvert / self-hosted. Noté comme plafond de référence futur.

Scope cut explicite : 1 modèle. Challenger ajouté seulement si BGE-M3 sous-performe au regard du recall@K.

2. Pipeline — 4 étages

Couche de linkage — l'invariant central

Les articles du KG sont des nœuds identifiés par pair_key (code_penal:222-23), pas par l'identifiant LEGI. Le graphe graph_penal.npz définit déjà l'ordre canonique des colonnes : article_ids[col] = pair_key (8 085 nœuds pénaux). Tout repose sur trois alignements :

  • pair_key ↔ texte LEGI — normalisation du n° d'article (forme compacte L743-7 ↔ LEGI L. 743-7) ; taux de résolution mesuré comme diagnostic (cf. coverage_check du 5 mai).
  • texte ↔ ligne d'embedding — emb_articles.npy rangé dans l'ordre de article_ids ; emb_jp.npy dans l'ordre de jp_ids (symétrie avec la convention jp_order).
  • ligne ↔ nœud graphe — artefact pairkey_to_graphcol.npy : alignement positionnel lossless, donc l'Étape 2 (complétion Laplacien sur le graphe) récupère des embeddings indexés sur les nœuds sans aucune jointure.
1

Diagnostic longueurs — falsifiable avant tout embedding

Tokeniser les 8 085 articles pénaux (nœuds du graphe) et les ~93 k summaries JP (CC, ~95 % du sous-graphe pénal) avec le tokenizer BGE-M3, sortir la distribution (p50/p90/p99/p100). Décision conditionnelle : si p100 < 8192 → contrainte « zéro troncature » native, aucun cas limite. Sinon → fallback chunk + mean-pool appliqué uniquement aux dépassements (information préservée, pas tronquée).

01_token_stats.py → token_stats.json
2

Ingestion LEGI + résolution du linkage pair_key → texte

Via la librairie legi (Legilibre) : archive DILA echanges.dila.gouv.fr/LEGI/ → SQLite, extraire le texte des 4 codes (CP, CPP, route, CJPM). Pas de parsing XML manuel. Cœur de l'étage : une fonction de normalisation qui résout les 8 085 pair_key du graphe vers leur article LEGI (préfixes L/R/D/A, suffixes latins, renumérotations). Produit un diagnostic de couverture — taux de résolution global + spécifiquement sur les 51 articles gold (analogue au coverage_check du 5 mai). Un gold non résolu plafonne le recall : on veut le savoir avant d'embedder.

02_fetch_articles.py → articles_penal.parquet (pair_key, texte) + articles_coverage.json
3

Embedding BGE-M3 — un vecteur par unité, sans troncature

Deux corpus encodés séparément, chaque matrice rangée dans l'ordre des nœuds du graphe : emb_articles.npy (8 085 × 1024) ⟂ article_ids, emb_jp.npy (~93 k × 1024) ⟂ jp_ids, plus articles_order.npy / pairkey_to_graphcol.npy pour rendre le linkage lossless. Volume léger → local Mac MPS viable, ce qui contourne la fragilité env cluster ; L40S = repli. Choix explicite.

03_embed.py → emb_articles.npy, emb_jp.npy, articles_order.npy, pairkey_to_graphcol.npy
4

Éval recall top-K sans graphe — la métrique de Johnny

Pour chacune des 8 questions : cosinus question↔article et question↔JP ; courbe recall@K (K = 10, 20, 30, 50, 100, …) ; sortir le K* à partir duquel la majorité du gold est récupérée. Article-side = gold propre (articles_attendus.obligatoires/optionnels). JP-side = résolution short_ref → corpus par regex pourvoi.

04_eval_recall.py → recall_curves.csv + K* par question

Limitations connues — assumées, pas masquées
  • Plafond par construction : l'ensemble embeddé = les nœuds article du graphe. Un gold qui n'est cité par aucune JP n'est pas un nœud, donc inatteignable — déjà 1/51 (code_penal:222-26-2, ~98 % de couverture gold→graphe). Le recall article est borné par ce 98 %, à reporter explicitement.
  • Le taux de résolution pair_key → texte LEGI (mesuré étage 2) plafonne aussi le recall : normalisations de numérotation imparfaites = articles sans texte donc non embeddables.
  • Éval JP biaisée : jp_attendues a ref:null → résolution par regex pourvoi CC-only (fragilité héritée du 5 mai). 1 question sur 8 a 0 JP gold.
  • 8 questions = échantillon faible — c'est précisément ce que l'Étape 3 corrigera.
  • LEGI = droit actuel : un article abrogé / renuméroté depuis une JP ancienne peut ne pas matcher → à tracer dans le diagnostic d'ingestion.
Principe directeur — diagnostic-first

Chaque étape lourde est précédée d'un test peu coûteux qui peut l'invalider. L'étage 1 mesure avant d'embedder ; l'éval mesure le recall intrinsèque avant toute exploitation du graphe. Cohérent avec la méthodologie « vérifier sur preuve, pas supposition ».
