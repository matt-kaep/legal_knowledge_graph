# 2026-05-05 — Baseline B2 : du setup aux résultats catastrophiques

Journée dense — passage du design à l'exécution sur cluster, puis une analyse Phase A locale qui a renversé l'interprétation des résultats. **Le bottleneck n'est pas le retrieval, c'est l'embedding.**

---

## 1. Setup initial et pivot stratégique

### 1.1 Décision : focus pénal pour itérer vite

Au lieu de la baseline B2 sur tout le corpus (1,07 M JP, ~20 h sur Mac MPS), pivot vers un **subset pénal** :
- 118 112 JP pénales filtrées via citation d'un article d'un code pénal (`code_penal`, `code_de_procedure_penale`, `code_de_la_route`, `code_de_la_justice_penale_des_mineurs`)
- Répartition : CC=97 060, CA=14 315, TJ=6 737
- 8 questions CRFPA pénales (3 droit pénal + 5 procédure pénale)

Permet une expérience qui tourne en ~10 min sur cluster L40S.

### 1.2 Réorientation : stratégies d'agrégation > comparer 5 modèles

Plus instructif que tester 5 encodeurs sur 3 K → tester **4 stratégies d'agrégation × 5 K** sur 1 modèle :

| Strategy | Logique |
|----------|---------|
| `union` | Article cité par ≥ 1 JP du top-K |
| `intersection` | Article cité par TOUTES les K JP |
| `majority` | Article cité par ≥ ⌈K/2⌉ JP |
| `weighted` | Top-N articles classés par Σ similarité des JP citantes |

→ 20 configs × 8 questions = 160 évaluations, toutes comparables dans un CSV.

### 1.3 Infrastructure produite

`baseline_b2/penal_bundle.tar.gz` (293 MB) :
- `jp_index_penal.parquet` — id, number, juris, text des 118k JP
- `graph_penal.npz` — sous-graphe CSR pénal
- `rubrics_penal.json` — 8 questions fusionnées
- `eval_rubric.py` — scorer CRFPA
- `run_cluster.py` — script all-in-one (download → embed → eval → purge)

## 2. Découvertes critiques pendant le setup

### 2.1 Le pourvoi (`number`) n'est PAS un identifiant unique

| Juridiction | Doublons intra | Format | Notes |
|-------------|----------------|--------|-------|
| CC | 13 137 / 553k | `XX-XX.XXX` | Format standard, mais collisions et `-.` malformés |
| CA | 62 532 / 430k | hétérogène (`1998-2549`, `1362/00`, …) | Rien d'exploitable |
| TJ | 22 027 / 142k | `YY/NNNNN` | Idem |
| **Inter-juridictions** | 16 532 sur 50k arrêts | | Collisions CC↔CA possibles |

→ La clé fiable est `id` Judilibre (ObjectId). Le scoring CRFPA via regex `\b(\d{2})[\s\-]*(\d{2})[.\-]?(\d{3})\b` ne matche que le format CC, donc en pratique **seules les JP CC sont évaluables sur la dimension JP**.

### 2.2 Métadonnées très hétérogènes

Stats sur 10k arrêts par juridiction :

| Juridiction | `summary` dispo | `titlesAndSummaries` | médiane `text` | p90 `text` |
|-------------|-----------------|----------------------|----------------|------------|
| CC | **95,5 %** (471 chars médiane) | 0,3 % | 2 848 chars | 5 533 chars |
| CA | **0 %** | 0 % | 10 265 chars | 19 948 chars |
| TJ | **0 %** | 0 % | 9 290 chars | 22 336 chars |

→ Pour CC : on a privilégié `summary` (~150 tokens). Pour CA/TJ : que `text` brut. Justifie le chunking + mean pooling.

### 2.3 Tentative Mac MPS → OOM

Première version de `embed_corpus.py` accumulait tous les chunks en RAM (~25 GB) → **crash à 68 %**. Réécrit en streaming par batches de 4 000 docs avec écriture incrémentale dans un `np.memmap`. Mais Mac MPS reste lent (~11 doc/s avec e5-small) → décision : **cluster L40S**.

## 3. Cluster run : résultats du benchmark

### 3.1 Configuration exécutée

- Modèle : `intfloat/multilingual-e5-base` (768d)
- Chunking : 510 tokens, overlap 64, max 8 chunks/doc, **mean pooling** par document, L2-normalisé
- 4 stratégies × 5 K = 20 configs × 8 questions = 160 évaluations
- Embedding 118k JP en ~6 min sur L40S (`embed_time_s = 2386` s mesuré)

### 3.2 Résultats clés (`comparison_b2_penal.csv`)

| Stratégie | K | S_retrieval | S̄_art | S̄_jp | N_art | Verdict |
|-----------|---|-------------|--------|-------|-------|---------|
| **union** | **10** | **0,158** | **0,315** | **0,000** | 49 | Meilleur (par recall) |
| union | 7 | 0,138 | 0,276 | 0 | 39 | |
| union | 5 | 0,091 | 0,182 | 0 | 31 | |
| weighted | 7 | 0,079 | 0,157 | 0 | 5 | Sous-dimensionné (top=5) |
| majority | tous | ≈ 0 | ≈ 0 | 0 | <4 | Trop restrictif |
| **intersection** | **tous** | **0** | **0** | 0 | <1 | Inutilisable |

### 3.3 Observation choquante : S̄_jp = 0 PARTOUT

Sur les **160 évaluations, aucune n'a obtenu un seul match JP**. Sur Q1 par exemple :
- Pourvois prédits : `03-83.237, 17-81.762, 06/00310, 07/02009, …`
- Pourvois GT : `18-82.829, 20-80.135, 00-85.467, 90-83.786, 98-80.730`
- **Match : zéro**

Hypothèse à vérifier : la GT est-elle même dans le corpus ? Le retrieval est-il à des km du signal ?

## 4. Phase A — Audit local (post-cluster)

Toutes les analyses ci-dessous tournent sur Mac avec les embeddings rapatriés du cluster.

### 4.1 ✅ A.1 — Couverture GT (`coverage_check.py`)

Pour chaque pourvoi GT extractible par regex, présence dans le corpus :

| Strate | GT extraits | Trouvés | Couverture |
|--------|-------------|---------|------------|
| core | 8 | 8 | **100 %** |
| expected | 5 | 5 | **100 %** |
| expert | 3 | 3 | **100 %** |

**Conclusion** : la GT est intégralement présente. Le S̄_jp = 0 ne vient PAS d'un défaut de couverture, c'est **purement un défaut de retrieval**.

### 4.2 🔴 A.2 — Rang des GT dans le ranking embedding (`gt_rank_check.py`)

Pour chacun des 16 pourvois GT extraits, à quel rang remontent-ils dans le tri décroissant des similarités cosinus avec la question ?

| Métrique | Valeur |
|----------|--------|
| Rang médian | **76 782** / 118 112 |
| Rang moyen | 58 319 |
| Rang min | 549 |
| Rang max | 110 485 |

| Recall | top-10 | top-100 | top-1 000 | top-10 000 | top-50 000 |
|--------|--------|---------|-----------|------------|------------|
| GT remontés | **0/16** | 0/16 | 2/16 (12 %) | 3/16 (19 %) | 8/16 (50 %) |

**Diagnostic** : `multilingual-e5-base` ne capture quasiment **aucun signal pertinent** sur ce corpus. Le modèle est généraliste multilingue, jamais entraîné sur du juridique FR. Les résumés CC en MAJUSCULES ("STATUANT SUR LA RESPONSABILITE…") sont sémantiquement très éloignés des questions modernes ("Quelles sont les conditions de la garde à vue ?"). **Ce n'est pas un problème de K trop petit — même K=10 000 ne sauve pas grand-chose**.

### 4.3 🟢 A.3 — Multi-hop JP→articles→JP (`run_multihop.py`)

Le graphe peut-il rattraper les défaillances de l'embedding ? Le 2-hop fonctionne ainsi :
1. Top-K=10 JP entry via embedding
2. Articles cités par ces 10 JP = 1-hop article set
3. Toutes les JP qui citent ≥ M de ces articles = expansion 2-hop
4. Articles cités par {entry + expansion} = output

Résultats avec K_entry=10 :

| Config | Recall S̄_art | N articles retournés | **Precision** | N JP expandues |
|--------|--------------|----------------------|---------------|----------------|
| 1hop | 31 % | 49 | **3,7 %** | 0 |
| 2hop_M2 | **89 %** | **9 189** | **0,06 %** | 13 443 |
| 2hop_M3 | 79 % | 5 028 | 0,12 % | 5 760 |
| 2hop_M5 | 67 % | 1 848 | 0,53 % | 1 659 |
| 2hop_M2_top200 | 52 % | 608 | 0,56 % | 200 |
| 2hop_M2 + 1000 JP retournées | 89 % | 9 189 | 0,06 % | 13 443 (S̄_jp = **0,07** !) |

**Insights** :
- Le multi-hop M=2 fait passer le rappel articles de 31 % → 89 % MAIS retourne 9 189 articles (precision 0,06 %). Le scorer CRFPA récompense l'over-fishing parce qu'il mesure du recall pur. **Inexploitable côté humain**.
- Le 2-hop ne ramène que **1,12 GT JP en moyenne** sur ~13 500 JP expandues (~0,008 % de précision JP). Même via le graphe, l'embedding sous-jacent rate trop de signal.
- Le **premier S̄_jp non-nul (0,07)** apparaît seulement quand on retourne 1 000 JP au scorer (vs K=10 par défaut).

## 5. Discussions techniques notables

### 5.1 Mean pooling vs chunk retrieval

Question soulevée : pour 1 JP avec 8 chunks, on garde **1 seul vecteur moyen** (mean pooling) — alternative : garder les 8 et faire du retrieval au niveau chunk.

| Approche | Stockage | Granularité | Comportement |
|----------|----------|-------------|--------------|
| **Mean pooling (actuel)** | 363 MB (118k × 768 × 4) | "Cet arrêt parle globalement de…" | Un passage clé dans 1/8 chunks est dilué |
| **Chunk retrieval** | ~2,2 GB (700k chunks) | "Ce paragraphe précis traite de…" | Le passage clé sort intact en top-K |

C'est le compromis classique en dense retrieval (Sentence-BERT vs ColBERT). À tester en Phase B.

### 5.2 Le KG comme dictionnaire vs comme espace

Constat important : dans la baseline B2 actuelle, **le graphe a juste servi de table de lookup** (`jp_id → articles cités`). Aucune traversée, aucune propagation, aucun usage de la structure (centralité, communautés, co-citation). Le multi-hop est le **premier usage non trivial du graphe**.

### 5.3 Représentation textuelle hétérogène entre juridictions

Pour CC on a embeddé le `summary` (court, dense, propre) ; pour CA/TJ le `text` brut (long, bruité). **Pour comparer proprement entre modèles d'embedding (Phase B), il faut uniformiser** : utiliser `text` partout.

## 6. Conclusions et orientations

### 🟢 Ce qu'on a appris

1. **Couverture GT = 100 %** — le corpus est bien constitué, la baseline est testable.
2. **Le KG porte du signal** — multi-hop M=2 atteint S̄_art recall = 89 %.
3. **Le pourvoi-match strict ne marche pas** — comme prédit, la dimension JP du scoring est presque invalidée par les formats hétérogènes.
4. **Le scoring CRFPA récompense l'over-fishing** — pas idéal, mais c'est la métrique du benchmark.

### 🔴 Ce qui ne marche pas

1. **multilingual-e5-base est inadapté à ce corpus** — rang médian des GT à 76 782 / 118 112.
2. **Le 1-hop ne suffit pas** — 31 % de recall articles seulement.
3. **Le 2-hop sauve par sur-extension** — 9 000 articles retournés, precision 0,06 %.

### 🎯 Phase B — re-embedding sur cluster avec plusieurs modèles

Le bottleneck **n'est pas le retrieval, c'est l'embedding**. Plan :

1. **Modèles à tester** : `e5-large` (1024d), `bge-m3` (long context 8k tokens, SOTA multilingue), `dangvantuan/sentence-camembert-large` (FR-spécifique). Idéalement aussi un modèle légal-FR si trouvable.
2. **Texte uniforme** : `text` brut pour tous (pas de summary CC privilégié) → comparaison propre inter-modèles.
3. **Garder les chunks** en plus du mean pool (~2 GB total) → permet de tester max-pool / chunk retrieval en Phase C.
4. **Métrique principale** : rang des GT (top-10 / top-100 / top-1 000) plutôt que S_retrieval, pour mesurer la **qualité intrinsèque** de l'embedding indépendamment du scoring CRFPA biaisé.

### 🎯 Phase C — analyses comparatives en local (après B)

- **C.1** Divergence des top-K JP entre modèles (Jaccard, Kendall tau)
- **C.2** Mean pool vs max pool vs first-chunk pour chaque modèle
- **C.3** Multi-hop sur le meilleur backbone
- **C.4** Truth check : quel modèle remonte le plus de pourvois GT en top-K ?

### 🎯 Idée Phase D (à creuser après) — embedder les ARTICLES, pas les JP

**Intuition forte** : on essaie de matcher la question avec des arrêts (textes longs, narratifs, faits + procédure + motifs + dispositif → beaucoup de bruit thématique). Mais une question CRFPA cible un **point de droit précis**, qui est **codifié dans un article**. Renverser l'approche :

```
Question → embed → top-K articles (pas JP) → JP qui les citent via le KG
```

**Avantages potentiels** :
- Articles = textes courts, denses, juridiquement structurés (~88k articles vs 118k JP)
- Pas de bruit factuel/procédural → signal thématique pur
- Mapping `question juridique → article codé` plus direct que `question → arrêt`
- Les JP sont retrouvées par back-edge graphe : article cité → toutes les JP qui le citent
- Fini la dépendance au summary/text/chunk hétérogène entre CC/CA/TJ

**Prérequis** : nécessite le **texte intégral des articles** (Légifrance fetch), ce qui est exactement la **Priorité 2** de la roadmap du 2026-04-29. On n'a aujourd'hui que les `pair_key` (`code_penal:222-23`), pas le contenu.

**À tester en Phase D** une fois Légifrance branché :
1. Fetch texte de ~8 000 articles pénaux via API Légifrance
2. Embed les articles avec le meilleur modèle de Phase B
3. Pour chaque question : top-K articles → expansion vers JP via back-edge graphe
4. Comparer à la baseline B2 (JP-based) sur les mêmes 8 questions

Hypothèse à valider : le score articles devrait être **bien meilleur** car la sémantique question↔article est plus directe. Le score JP pourrait aussi être meilleur car les JP retrouvées via les articles GT (par back-edge) sont par construction "topicalement correctes".
