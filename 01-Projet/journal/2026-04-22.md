## Contexte

Hier soir, le point avec Jhony a acté une **fusion des deux benchmarks** en un benchmark unifié "mode avocat" + la nécessité de **fiches de métriques par graphe** ([[Design-Benchmark-Avocat-Unifie]]).

Avant d'attaquer, un préalable : **valider la fiabilité de notre parser regex de rapprochements**. Sans cela, toute la GT sur les JP liées est sur du sable.

---

## Plan du matin — 3 chantiers séquentiels

### Chantier 1 — Validation du regex d'extraction des articles

**Clarification** : il s'agit du regex d'**extraction d'articles de loi** défini dans `enrichissement_base_complete.ipynb` (fonctions `extract_articles` et `extract_code_article_pairs`), **pas** du regex de parsing des rapprochements.

Regex concerné :
```python
ARTICLE_NUM_RE = r"([LRDAE]\.?\s*\d[\d\-\.]*\d?|\d{1,5}(?:\-\d+)*)"
# Match "articles ... du <code>" ou "<code> <num>"
```

**Objectif** : mesurer la couverture et la précision du regex qui produit les `code_article_pairs` dans toute la base enrichie (1,1 M arrêts).

**Protocole** :
1. Échantillonner **100 arrêts** stratifiés (50 CC + 25 CA + 25 TJ).
2. Pour chaque arrêt, **double extraction** :
   - **Regex** : relance `extract_code_article_pairs(text)` sur le texte intégral → liste de pair_keys normalisés
   - **LLM** : prompt structuré demandant d'extraire tous les articles cités (code + numéro) → liste de pair_keys au même format
3. **Comparer** par arrêt :
   - TP = pair_keys communs regex ∩ LLM
   - FP_regex = pair_keys produits par regex mais pas LLM (faux positifs potentiels)
   - FN_regex = pair_keys produits par LLM mais pas regex (oublis du regex)
4. Métriques globales : Precision, Recall, F1 + distribution par juridiction.
5. **Catégorisation des écarts** (qualitative sur les FN) :
   - Formulations non couvertes (abréviations, ellipse de code, article romain…)
   - Codes absents de `CODE_PATTERNS_OFFICIAL`
   - Problèmes de normalisation

**Livrable** : fiche de calibration du regex + éventuelles suggestions de patterns à ajouter.

### Chantier 2 — Graphes propres et documentés

Une fois le regex validé :
1. Reconstruire le **graphe JP↔JP** avec filtre ≥3 rapprochements (règle déjà appliquée dans v1).
2. Reconstruire le **graphe JP↔Article** (pas via rapprochements, directement depuis `code_article_pairs`).
3. Pour chaque graphe : extraire **métriques structurelles complètes** + **interprétation écrite**.
4. **Comparer les distances** entre paires de JP dans le graphe JP-JP (rapprochements) vs le graphe JP-Article (chemin par article commun).
   - Si deux JP sont à distance ≤2 dans JP-JP, à quelle distance sont-elles dans JP-Article ?
   - **Cohérence croisée** : valide la structure si les deux topologies racontent la même chose.

### Chantier 3 — Test de retrieval pur (baseline C3)

Sans LLM, simple baseline retrieval sur les graphes :
1. Questions d'entrée : **CRFPA** + **Les-Audits-Affaires**
2. Embedding de la question
3. Recherche du **nœud le plus proche** dans le graphe (JP ou Article)
4. Retourner les **voisins de rang 1** (et éventuellement rang 2)
5. Comparer aux articles/JP attendus dans la GT → voir si le matching tient

**Enjeu** : mesurer à quel point un retrieval *purement structurel* suffit avant même d'ajouter un LLM.
